一、业务背景

公司当前已对外宣称"自建物流"作为统一物流品牌，但实际履约由第三方"易抵达"承担：

  • 头程：易抵达派单给某第三方头程物流商承运（具体哪家由易抵达自行决定）
  • 尾程：易抵达本地派送
  • 轨迹：易抵达将头程 + 尾程整合成一条完整轨迹回传 ERP

本方案的目标：在 ERP 系统中正式建立"自建物流"虚拟物流商，对外用 ERP 自己生成的跟踪号承载完整客户体验，对内与易抵达运单号建立映射，借助易抵达完成实际履约。

3.2.5 后缀 v1.1 三轮：升级为三段 X{nn}[R{nn}][T{nn}]

后缀格式总览：

后缀 = X段（拆分位） + [R段（补发位）] + [T段（重置位）]
段含义出现条件取值
X 段拆分序号强制必带原始单 / 补发主单 → X00；拆分子单 → X01..X99
R 段补发序号仅补发场景出现第 N 次补发 → R{nn}，01..99
T 段 三轮新增重置序号仅订单被重置过出现第 N 次重置 → T{nn}，01..99；未重置不出现

完整后缀样例矩阵（前缀+订单号 = VIVAIA5839484942）：

订单形态重置情况后缀格式样例
原始单（不拆不补）未重置X00VIVAIA5839484942X00
原始单重置 1 次X00T01VIVAIA5839484942X00T01
原始单重置 2 次X00T02VIVAIA5839484942X00T02
拆分子单（第 N 子单）未重置X{nn}VIVAIA5839484942X01、...X02
拆分子单重置 N 次X{nn}T{mm}VIVAIA5839484942X01T01
补发主单（原单第 N 次补发）未重置X00R{nn}VIVAIA5839484942X00R01
补发主单重置 N 次X00R{nn}T{mm}VIVAIA5839484942X00R01T01
拆分子单又被补发未重置X{nn}R{nn}VIVAIA5839484942X01R01
拆分子单又被补发重置 N 次X{nn}R{nn}T{mm}VIVAIA5839484942X01R01T02
补发的补发（罕见）未重置在所属拆分位上 R 序号累加VIVAIA5839484942X00R02、...X01R02
补发的补发重置 N 次同上叠加 T 段VIVAIA5839484942X00R02T01
拆分再拆分（罕见）未重置见下方"拆分再拆分"说明
设计要点：
• 序号采用 2 位补零（X01..X99 / R01..R99 / T01..T99），业务上拆分/补发/重置均不超过 99 次，足够；
• 原始单也带 X00 后缀，保持所有跟踪号"必有 X 段"的统一格式，便于后端解析；
• 拆分子单的补发叠加 R 后缀而非生成新订单跟踪号——保留"这是哪条拆分子单的补发"信息；
• T 段仅在重置过的订单上出现——未重置的订单跟踪号不带 T，避免对绝大多数订单平添长度负担；从有无 T 段即可"一眼看出是否被重置过及次数"；
• 拆分再拆分：业务上不在跟踪号 X 段做嵌套，而是通过订单层面的"拆分链路"维护，跟踪号取最终生效拆分位对应的 X{nn}（即把原拆分子单视为"父单"，二次拆分后的新子单取自己的 X 序号，并在数据模型中通过 virtual_order_id 链路追溯）。如业务确有需求把多层拆分编进跟踪号，再升级规则。

3.2.5.1 订单重置的业务定义 v1.1 三轮新增

订单重置：在已分配自建物流但未出库的窗口期，运营/业务在订单管理后台对订单执行"重置物流"动作。重置流程：

  1. 现有自建跟踪号映射置为 RESET 状态（不可复用、不可被任何接口/查询命中）
  2. 调易抵达"作废运单"接口（如已取号成功）
  3. reset_seq 序号 +1，按 §3.2.5 规则重新生成新跟踪号（带新的 T{nn} 段）
  4. 重新执行 §4.1 流程：取号 + 取面单 + 建立新映射
  5. 触发销售平台回传新跟踪号（覆盖旧号）

触发场景示例：

  • 客户改地址需重新分单
  • 规则误命中需切换到其他物流商再切回
  • 易抵达取号成功但面单异常需要重出
⚠️ 已出库订单不可重置——已贴面单出库后只能走"快速换单"（见 §4.8.3）。

3.2.6 唯一性保证

  • 一个包裹对应一个订单（含拆分子单 / 补发单），1:1 关系；不同订单跟踪号必然不同
  • "平台订单号 + X 段 + R 段 + T 段"在同一来源内由平台 + ERP 联合保证唯一
  • 重置场景 v1.1 三轮新增：订单每次重置 reset_seq +1，T 段递增（T01 → T02 → ...），新跟踪号在系统中全局唯一；旧跟踪号映射置为 RESET 状态，永不复用、永不命中查询
  • 残余风险（接受）：GALAXY 与 Shopify 跨来源极端情况下平台订单 ID 可能数字相同 → 跟踪号撞号；本期评估概率极低，暂不加来源码兜底，由后续监控 + 入库唯一性约束兜底

3.2.7 字符集与长度

  • 字符集：[A-Z0-9] 大写字母 + 数字
  • 典型长度：19~28 位（Shopify GID 通常 10~15 位，加品牌+后缀；未重置场景）
  • 极端上限：VIVAIA(6) + 平台订单号(32) + X{nn}R{nn}T{nn}(9) = 47 位 v1.1 三轮：增加 T 段后由 44 → 47
  • 风险：超过部分销售平台 tracking number 字段长度限制（一般 35 位）。研发联调时需核实易抵达和销售平台对长度的实际接受范围；如确实超限，可对清洗后平台订单号做"末尾保留 N 位 + 头部哈希"的截断兜底（兜底方案在本期不实现，先做监控告警）。重置 3 次以上的极端订单（T03+）极少见，重点关注监控告警即可

3.2.8 生成时机

跟踪号在订单分配自建物流那一刻就生成（早于易抵达取号）。详见 §4.1。

4.8 仓库实操中的注意事项 v1.1 二轮新增

经核查仓库代码（erp-warehouse），自建物流场景下有 3 处实操逻辑必须额外处理。v1.0 / v1.1 一稿中"仓库零改动"的结论修订为"仓库轻量改动"。

4.8.1 核重发货：跟踪号一致性校验冲突

现状（DelivereServiceImpl.java:725）：

if (!订单.trackingNumber.equalsIgnoreCase(包裹.trackingNumber)) {
    throw "ERP订单号[X]当前跟踪号为[A]，与包裹跟踪号[B]不一致，不能进行发货"
}

仓库扫描完成后会强校验"虚拟订单上的跟踪号 == 包裹上的跟踪号"，大小写不敏感。

冲突：

  • 面单上印的是易抵达运单号（仓库 PDA 扫的就是这个号）
  • 销售平台回传给客户的是自建跟踪号（订单上需要存这个号）
  • 如果一个字段存自建号、另一个存易抵达号，校验必然失败

约定（写进数据模型）：

字段位置存什么备注
VirtualOrder.trackingNumber（虚拟订单上）自建跟踪号与销售平台回传保持一致
Package.trackingNumber（包裹上）自建跟踪号与订单一致，核重校验通过
Package.providerTrackingNumber（新增字段）易抵达运单号仓库面单上打印的就是这个号；扫码时映射回自建号

仓库改动：

  1. 仓库 Package 实体新增 providerTrackingNumber 字段（仅自建物流场景非空）
  2. 仓库扫码查找方法 packageMapper.findByTrackingNumberOrPackageNumber 增加 providerTrackingNumber 查询路径——扫到易抵达号也能查到包裹
  3. 面单打印时取 providerTrackingNumber 而不是 trackingNumber

4.8.2 specialConversion 截断匹配的污染风险

现状（TrackingNumberUtil.java:25）：当扫描的跟踪号长度 > 20，会自动尝试 7 种"前/后截断"片段去查（兼容 fedex / 行运易 / 乐天等真实承运商的特殊编码）。

冲突：

  • 自建跟踪号长度典型 19~28 位，极端值 44 位（远超 20 位阈值）
  • 一旦触发截断，会被切成 6~7 个片段去查包裹 → 任意一个片段碰巧撞中其他真实物流商的号 → 匹配错误的包裹

仓库改动：

  • 在 specialConversion 入口加白名单短路：以 VIVAIA / FANKA / 已配置的自建品牌前缀开头的跟踪号，直接返回原值不做截断
  • 或在 findByTrackingNumberOrPackageNumber 查询时按 provider_code='self-built' 路由分支

取号成功率 < 95% / 面单缺失率 > 5%关闭规则引擎"自建物流"分配目标的开关；新订单不再走自建
跟踪号唯一性冲突 > 0立即关闭灰度，复盘根因（疑似跨来源平台 ID 撞号）；评估是否启用 v1.1 暂未实施的"来源码兜底"
已分配自建物流的在途订单维持现状继续走完履约，不做单笔回滚（避免对已回传销售平台的订单造成冲击）

十、关键风险与对策

风险对策
易抵达接口稳定性差，导致大量订单卡在"分配物流失败"加技术侧自动重试 + 监控告警 + 业务侧"非命中规则的兜底物流商"开关
易抵达轨迹文案泄露头程承运商品牌留关键词替换开关；上线前抽查易抵达样本数据
自建跟踪号被销售平台/客户分享后被识别为"假号"跟踪号格式规范化 + track.vivaia.com 提供权威查询入口；新规则带可读品牌前缀，识别度更高
一单多包裹场景下客户体验混乱（"我下了 1 个单怎么有 2 个跟踪号"）销售平台订单页明确展示每个包裹独立的发货信息 + 客服话术准备；新规则的 X01/X02 后缀直观体现拆分关系
取号成功但面单链接过期（易抵达侧 PDF URL 有时效）物流服务侧落地缓存（PDF 二进制持久化，不依赖 URL）
v1.1 新增 跟踪号长度超销售平台 tracking number 字段上限联调前实测 Shopify / GALAXY 对长度的接受范围；若超限，对清洗后平台订单号做"末尾保留 N 位 + 头部哈希"的截断兜底
v1.1 新增 GALAXY 与 Shopify 跨来源平台订单 ID 撞号入库唯一索引强校验 + 监控告警，命中告警即评估启用"来源码兜底"（在品牌前缀后加 G/S，需小幅改造）
v1.1 新增 新增 Shopify 店铺未配置品牌前缀就接订单规则引擎在分配自建物流前校验店铺是否有 brand_prefix 配置，无则抛错 + 告警，倒逼运营先配置
v1.1 二轮新增 核重发货跟踪号不一致校验失败严格遵守 §5.2.1 存储约定：订单和包裹的 trackingNumber 字段都存自建号；面单上打印的易抵达号存到 Package.providerTrackingNumber。上线前用真实样本跑一遍核重流程做回归
v1.1 二轮新增 specialConversion 截断片段误匹配在 TrackingNumberUtil.specialConversion 入口对自建品牌前缀加白名单短路；上线前回归测试 fedex / 行运易 / 乐天等承运商的截断匹配是否仍正常
v1.1 二轮新增 快速换单的换内场景未识别，重复回传销售平台regeneratePackageTrackingNumber 出参带"自建号是否变更"标志，调用方据此决定是否回传销售平台；上线前回归换出/换入/换内 3 种场景
