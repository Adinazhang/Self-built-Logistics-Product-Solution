一、业务背景

公司当前已对外宣称"自建物流"作为统一物流品牌，但实际履约由第三方"易抵达"承担：

  • 头程：易抵达派单给某第三方头程物流商承运（具体哪家由易抵达自行决定）
  • 尾程：易抵达本地派送
  • 轨迹：易抵达将头程 + 尾程整合成一条完整轨迹回传 ERP

本方案的目标：在 ERP 系统中正式建立"自建物流"虚拟物流商，对外用 ERP 自己生成的跟踪号承载完整客户体验，对内与易抵达运单号建立映射，借助易抵达完成实际履约。

3.2.3 6 位散列序列的生成 v1.2 新设

目的：让 6 位序列对外"看起来无规律"——观察者无法从跟踪号反推今天发了多少单——同时数学保证日内不撞号，无需查重重试。

生成机制：

  1. 内部维护一个 Redis 计数器，键格式 tracking:counter:{brand}:{YYMMDD}（按品牌 + 日期分桶），初值 0
  2. 每次生成跟踪号时对计数器做原子自增 INCR，取得 N（1 ~ 999,999）
  3. 通过一个固定的"模乘法逆元"或 LCG 数学公式将 N 映射成 6 位散列输出（值域 0 ~ 999,999，左侧补零）
  4. 公式由研发选定，关键约束：
    • 必须是 0 ~ 999,999 范围内的双射（一一对应）——不同 N 必出不同输出，绝不撞号
    • 输出在视觉上无明显递增规律——隐藏单量
    • 计算 O(1)、纯数学运算、无外部依赖
  5. 每日 0 点（UTC+8）由日期键自然切换实现"归零"效果（前一天的键 24 小时后自动过期清理）

容量上限：100 万单/天/品牌（VIVAIA 当前量级有大量余量，预留扩张空间）。

公式保密性：散列公式属于内部实现细节，不写入对外文档/接口；理论上即便被反推，外部最多能拿到内部计数器序号 N（无业务利用价值）。安全风险可忽略。

3.2.4 1 位 Luhn 校验位 v1.2 新设

目的：仓库人工录入/手抄/扫码识别错误时立即被系统拦截，不会等到下游核重发货才暴露。

生成方式：对"品牌前缀 + YY + MMDD + 6 位散列序列"整体做 Luhn 算法（信用卡号常用的标准校验算法），输出 1 位 0~9 数字附在末尾。

品牌前缀的字母处理：Luhn 算法只接受数字。品牌前缀中的字母按 "A=10、B=11、…、Z=35" 映射为两位数字后再参与运算（业内常见做法），具体由研发实现。

校验方式：任何接收跟踪号的入口（仓库扫码、客服系统、track.vivaia.com）在进入业务逻辑前先做 Luhn 校验，校验失败直接拦截并提示"跟踪号格式错误"。

业务方/客服无感（看到的还是一串数字），研发只需引入标准 Luhn 函数，不到 30 行代码。

3.2.5 拆分 / 补发 / 重置场景下的跟踪号生成 v1.2 重写

新规则下，每个独立包裹（含拆分子单 / 补发单 / 重置后的新单）都各自取一个新散列序号生成全新跟踪号——跟踪号字面上看不出关联，业务关系全部由数据库字段承载：

场景新跟踪号生成业务关系追溯字段
拆分子单（同一订单 N 个包裹）每个子单各取一个新散列序号 → 各自生成全新跟踪号virtual_order_id（拆分链路）+ split_seq（拆分序号）
补发单补发单作为独立虚拟订单 → 取新散列序号 → 生成全新跟踪号parentReissueVirtualOrderNo（补发父单关联）+ reissue_seq（补发序号）
订单重置旧跟踪号置 RESET、不可复用；取新散列序号 → 生成全新跟踪号reset_seq 字段 +1（重置次数）+ 旧映射记录留存
设计要点：
• 旧 v1.1 三轮的 X{nn} / R{nn} / T{nn} 三段后缀全部移除，跟踪号字面不再承载这些信息；
• 客服/工单系统反查"某订单的所有跟踪号"由订单 ID 反向查询 self_built_tracking_mapping 表实现，人眼直接看跟踪号无法判断关联；
• 重置后的旧跟踪号永不复用、永不命中查询（沿用 v1.1 三轮的 RESET 状态约束）；
• 拆分再拆分：每一层拆分子单都取自己的新散列序号，关系仅靠 virtual_order_id 拆分链路维护。

3.2.5.1 订单重置的业务定义 v1.2 重写

订单重置：在已分配自建物流但未出库的窗口期，运营/业务在订单管理后台对订单执行"重置物流"动作。重置流程：

  1. 现有自建跟踪号映射置为 RESET 状态（不可复用、不可被任何接口/查询命中）
  2. 调易抵达"作废运单"接口（如已取号成功）
  3. reset_seq 序号 +1
  4. 按 §3.2.1 规则重新取一个新散列序号生成新跟踪号（跟踪号字面与旧号完全无关，只能通过 virtual_order_id + reset_seq 字段在数据库追溯重置历史）
  5. 重新执行 §4.1 流程：取号 + 取面单 + 建立新映射
  6. 触发销售平台回传新跟踪号（覆盖旧号）

触发场景示例：

  • 客户改地址需重新分单
  • 规则误命中需切换到其他物流商再切回
  • 易抵达取号成功但面单异常需要重出
⚠️ 已出库订单不可重置——已贴面单出库后只能走"快速换单"（见 §4.8.3）。

3.2.6 全局唯一性三层保障 v1.2 重写

层机制防什么
数学层散列公式是 0 ~ 999,999 范围内的双射；同一 {brand}+{YYMMDD} 计数器命名空间内不同 N 必出不同 6 位输出同日同品牌内不撞号
前缀层YYMMDD 段每日变化，跨日跟踪号前 12 位（VIVAIA）/ 11 位（FANKA）必不同跨日不撞号
数据库层self_built_tracking_mapping.self_built_tracking_no 加 UNIQUE 唯一索引数学/前缀层失效时的极端兜底；命中即报错告警，由人工核查
重置场景下的唯一性：重置生成新跟踪号时取当日新散列序号（reset_seq 不再编进跟踪号字面，仅作为数据库字段记录重置次数），落库时受 UNIQUE 索引兜底；旧号保留为 RESET 状态，不可复用。

风险消除（对比 v1.1）：v1.1 三轮存在的"GALAXY 与 Shopify 跨来源平台订单 ID 撞号"风险在 v1.2 下自然消除——新规则不再依赖平台订单号。

3.2.7 字符集与长度合规 v1.2 重写

  • 字符集：[A-Z0-9] 大写字母 + 数字
  • 固定长度：
    • VIVAIA 品牌（前缀 6 位）：6 + 2 + 4 + 6 + 1 = 19 位
    • FANKA 品牌（前缀 5 位）：5 + 2 + 4 + 6 + 1 = 18 位
    • 未来扩展品牌前缀建议保持 5–6 位长度，整体跟踪号稳定在 18–19 位
  • 长度合规：18–19 位远低于销售平台 tracking number 字段一般 35 位的上限，v1.1 三轮的"长度超限风险"在 v1.2 下消除，无需头部哈希截断兜底方案

3.2.8 生成时机

跟踪号在订单分配自建物流那一刻就生成（早于易抵达取号）。详见 §4.1。

并发原子性：散列序列由 Redis 原子 INCR 取号；分布式部署下 Redis 单节点保证全局有序、无重复；Redis 故障兜底由数据库 UNIQUE 索引报错。

跨日临界：以 Redis 取号那一刻（同一原子操作内）的服务器时间 UTC+8 决定 YYMMDD 段，避免"取号在 23:59:59、拼号在 00:00:00"导致日期段与计数器分桶错位。

4.8 仓库实操中的注意事项 v1.1 二轮新增

经核查仓库代码（erp-warehouse），自建物流场景下有 3 处实操逻辑必须额外处理。v1.0 / v1.1 一稿中"仓库零改动"的结论修订为"仓库轻量改动"。

4.8.1 核重发货：跟踪号一致性校验冲突

现状（DelivereServiceImpl.java:725）：

if (!订单.trackingNumber.equalsIgnoreCase(包裹.trackingNumber)) {
    throw "ERP订单号[X]当前跟踪号为[A]，与包裹跟踪号[B]不一致，不能进行发货"
}

仓库扫描完成后会强校验"虚拟订单上的跟踪号 == 包裹上的跟踪号"，大小写不敏感。

冲突：

  • 面单上印的是易抵达运单号（仓库 PDA 扫的就是这个号）
  • 销售平台回传给客户的是自建跟踪号（订单上需要存这个号）
  • 如果一个字段存自建号、另一个存易抵达号，校验必然失败

约定（写进数据模型）：

字段位置存什么备注
VirtualOrder.trackingNumber（虚拟订单上）自建跟踪号与销售平台回传保持一致
Package.trackingNumber（包裹上）自建跟踪号与订单一致，核重校验通过
Package.providerTrackingNumber（新增字段）易抵达运单号仓库面单上打印的就是这个号；扫码时映射回自建号

仓库改动：

  1. 仓库 Package 实体新增 providerTrackingNumber 字段（仅自建物流场景非空）
  2. 仓库扫码查找方法 packageMapper.findByTrackingNumberOrPackageNumber 增加 providerTrackingNumber 查询路径——扫到易抵达号也能查到包裹
  3. 面单打印时取 providerTrackingNumber 而不是 trackingNumber

4.8.2 specialConversion 截断匹配的污染风险

现状（TrackingNumberUtil.java:25）：当扫描的跟踪号长度 > 20，会自动尝试 7 种"前/后截断"片段去查（兼容 fedex / 行运易 / 乐天等真实承运商的特殊编码）。

冲突：

  • 自建跟踪号 v1.2 后固定 18~19 位（< 20 位阈值），但仍建议加白名单短路——避免未来规则升级或异常输入触发截断
  • 一旦触发截断，会被切成 6~7 个片段去查包裹 → 任意一个片段碰巧撞中其他真实物流商的号 → 匹配错误的包裹

仓库改动：

  • 在 specialConversion 入口加白名单短路：以 VIVAIA / FANKA / 已配置的自建品牌前缀开头的跟踪号，直接返回原值不做截断
  • 或在 findByTrackingNumberOrPackageNumber 查询时按 provider_code='self-built' 路由分支

9.2 回滚预案

触发条件动作
取号成功率 < 95% / 面单缺失率 > 5%关闭规则引擎"自建物流"分配目标的开关；新订单不再走自建

十、关键风险与对策

风险对策
易抵达接口稳定性差，导致大量订单卡在"分配物流失败"加技术侧自动重试 + 监控告警 + 业务侧"非命中规则的兜底物流商"开关
易抵达轨迹文案泄露头程承运商品牌留关键词替换开关；上线前抽查易抵达样本数据
自建跟踪号被销售平台/客户分享后被识别为"假号"跟踪号格式规范化 + track.vivaia.com 提供权威查询入口；新规则带可读品牌前缀，识别度更高
一单多包裹场景下客户体验混乱（"我下了 1 个单怎么有 2 个跟踪号"）销售平台订单页明确展示每个包裹独立的发货信息 + 客服话术准备；v1.2 下跟踪号字面无拆分关系，需在销售平台展示侧用"包裹 1 / 2"等中文标签弥补
取号成功但面单链接过期（易抵达侧 PDF URL 有时效）物流服务侧落地缓存（PDF 二进制持久化，不依赖 URL）
v1.1 风险，v1.2 消除 跟踪号长度超销售平台 tracking number 字段上限v1.2 规则下跟踪号固定 18~19 位，远低于一般 35 位上限，风险消除；联调时仍建议抽样验证 Shopify / GALAXY 实际接受度
v1.1 风险，v1.2 消除 GALAXY 与 Shopify 跨来源平台订单 ID 撞号v1.2 规则不再依赖平台订单号，风险自然消除；同日同品牌内由散列公式双射保证不撞，跨日由 YYMMDD 段保证不撞
v1.1 新增 新增 Shopify 店铺未配置品牌前缀就接订单规则引擎在分配自建物流前校验店铺是否有 brand_prefix 配置，无则抛错 + 告警，倒逼运营先配置
v1.2 新增 散列公式实现 bug 导致非双射上线前对公式做 0 ~ 999,999 全域单元测试，验证输出值集合大小恰好等于 1,000,000（无重复、无遗漏）；DB UNIQUE 索引兜底告警

v1.2 新增 跨日临界时刻 YYMMDD 段与计数器分桶错位取号与拼号必须在同一原子操作内取统一时间戳；UTC+8 时区源全链路一致；上线前对 23:59:55 ~ 00:00:05 时间窗压测
